## What this means in practice

v4.3 graduates the Decision Engine from "pilot in production" to "production-grade pattern with documented gaps." The score is honest, not inflated:

- **Three Level-3 dimensions** (architecture, observability, blast radius, evaluation) reflect work done in v4.0 through v4.3 across multiple cycles, not single-shot improvements.
- **Two Level-1 dimensions** (protocols, memory) are explicit v5 themes. Lifting either requires substantial work and a real driver (a client asking for it) to justify the cost.
- **Five Level-2 dimensions** (security, governance, cost, regulatory) all have a clear path to Level 3 within one quarter of focused operator work, no additional code required.

## Honest notes on the scoring

**Why not Level 3 on Security?** The kill switch exists and works in code, but it has not been tested under realistic conditions. Per the v2.1 strategy bundle, "untested kill switches have failed during real incidents." Honest scoring requires the drill before the score moves up.

**Why not Level 3 on Cost management?** The routing scaffold and budget caps are in place, but there is no semantic caching, no real LiteLLM gateway, and no learned routing classifier. Level 3 is the production gateway plus measured savings, not the scaffold plus aspiration.

**Why not Level 3 on Regulatory?** ISO/IEC 42001 alignment is the umbrella the strategy bundle recommends. v4.3 documents the framework but has not started the actual gap analysis. Level 3 requires the work, not just the plan.

**Why Level 1 (not 2) on Protocols?** Some teams would score this as Level 2 because the phase nodes have structured tool schemas internally. The v2.1 rubric specifies MCP at Level 2 ("MCP for some tools"). The Decision Engine has zero MCP. Honest scoring requires acknowledging the difference between "structured internal tools" and "MCP-compliant interfaces."

**Why Level 2 (not 3) on Memory?** Cognee or equivalent hybrid memory would lift this to Level 3 per the rubric. The Decision Engine's queries are mostly single-hop, so the gap is not the binding constraint, but the rubric scores against capability, not need. Vector RAG only is explicitly Level 2 in the rubric.

## When to re-score

- **Quarterly** as the recurring instrument the v2.1 strategy recommends
- **After any major release** (v4.4, v5.0)
- **After any critical incident** that exposes a gap not in the rubric
- **After completing any of the prioritized next steps above**, since each one moves at least one dimension

The score is meant to be a recurring measurement, not a one-time exercise. A balanced 23/30 is meaningfully different from "three 3s and seven 1s" of the same total. The path forward is to pull the Level-1 dimensions up and consolidate the Level-2 dimensions, not to chase Level 3 in places where it does not pay off (e.g., A2A coordination for a single-orchestrator architecture).
