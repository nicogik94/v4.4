# v4.4 Shadow Scenario Policy Prototype

This document describes the bounded Monte Carlo + Bayesian online-updating prototype added in shadow mode only.

## Scope implemented

- bounded scenario-policy package under `mas/scenarios/`
- capped scenario generation per request
- lightweight online Bayesian updates
- SQLite sidecar persistence for scenario posteriors and observations only
- deterministic fallback to the current baseline
- additive API visibility for shadow recommendations and baseline comparison

## Scope not implemented

- live control over workflow execution
- orchestration rewrites
- multiple workflow runs per request
- scheduled/background workers
- raw prompt dumps
- execution transcripts
- contextual bandits, BNNs, or broader scenario policy

## Core model

The shadow layer evaluates a small set of bounded runtime-policy scenarios for each LLM request:

- `baseline_deterministic`
- `reliability_guarded`
- `latency_guarded`
- `cost_guarded`

These are **policy variants over the single real execution**, not new workflow graphs.

The live system still executes the current deterministic baseline exactly once.

## Online Bayesian updates

Per phase and scenario, the sidecar stores:

- Beta posterior for scenario acceptance reliability
- Beta posterior for optional user feedback
- lightweight Normal posterior on latency mean
- lightweight Normal posterior on cost mean

The scenario acceptance event is derived from the real observed request:

- provider call succeeded
- observed latency was within the scenario bound
- observed cost was within the scenario bound
- optional feedback, if present, was acceptable

This keeps the prototype honest in shadow mode: it updates beliefs from the one real request, without pretending a counterfactual scenario actually ran.

## Monte Carlo policy scoring

For each request, the engine:

1. loads the current per-scenario posteriors
2. runs a strictly capped Monte Carlo utility estimate
3. picks the best expected-utility scenario
4. computes an ensemble recommendation when several scenarios remain plausible
5. recommends HITL when uncertainty is still too high

The current baseline still executes unchanged regardless of the shadow recommendation.

## SQLite sidecar

The sidecar stores only scenario-policy data:

- rolling scenario posteriors
- per-request scenario observations

It does **not** store canonical `ProjectState`.

Default env/config:

- `SCENARIO_SHADOW_ENABLED=true`
- `SCENARIO_SHADOW_SQLITE_PATH=mas/scenario_shadow.sqlite3`
- `SCENARIO_SHADOW_MAX_SCENARIOS=4`
- `SCENARIO_SHADOW_MONTE_CARLO_SAMPLES=48`
- `SCENARIO_SHADOW_HARD_SAMPLE_CAP=64`

## API surfaces

Additive read routes:

- `GET /projects/{id}/scenarios/shadow`
- `GET /projects/{id}/scenarios/shadow/{phase}`

These routes expose:

- best expected-utility scenario
- safe recommended scenario
- HITL recommendation when uncertainty is too high
- ensemble probabilities
- comparison against the deterministic baseline on reliability, calibration, cost, and latency

## Important boundary

This is **shadow mode only**.

- it does not change live execution
- it does not add automatic reruns or invalidation
- it does not alter `ProjectState`
- it does not change `decision_objects`
