# v4.4 Tranche 2 Plan

This document plans tranche 2 only. It does not authorize or describe implemented features.

Tranche 2 scope:

1. PHASE 3: one real CSV connector normalized into `Evidence` and `Signal`
2. PHASE 4: provider gateway abstraction, semantic cache interface, and config-driven routing hooks

Everything else remains deferred.

## Goal

Build on the tranche-1 baseline without changing the core operating model:

- keep `ProjectState` as the primary state carrier
- keep deterministic orchestration
- keep policy outside the LLM
- keep `decision_objects` derived-first

## Planned PHASE 3 work: CSV connector

### Intended outcome

Add one safe read-side CSV connector that ingests structured external data and normalizes it into tranche-1 decision objects.

The connector should:

- be read-only
- record provenance on every imported row
- normalize imported material into `Evidence` and `Signal`
- plug into the connector registry added in tranche 1

### Likely files to change

- `mas/extensions/connectors.py`
- new connector module, likely `mas/connectors/csv_connector.py`
- new normalization helper, likely `mas/connectors/normalizers.py`
- `mas/state.py` only if additive connector metadata is truly needed
- `mas/decision_objects.py` only if connector-imported items need a clean merge path
- `mas/api.py` only if an explicit ingestion endpoint is approved for tranche 2
- documentation files under `docs/`
- new tests under `mas/tests/`

### Expected interfaces/modules

- `ConnectorRegistry` remains the registry entrypoint
- `Connector` implementations return a normalized `IngestionResult`
- CSV-specific module should:
  - validate headers
  - parse rows safely
  - map rows into normalized evidence/signal payloads
  - attach `Provenance(source_type=\"connector_import\", ...)`

Possible internal modules:

- `mas/connectors/csv_connector.py`
- `mas/connectors/schema.py`
- `mas/connectors/normalizers.py`

### Main design risks

- schema drift between arbitrary CSV columns and normalized evidence/signal shape
- silent low-quality imports that look valid but are semantically weak
- provenance gaps if imports are normalized too early without preserving raw source references
- accidental dual-write confusion if imported items are treated as canonical before the model is ready

### Tests to run

- CSV happy-path ingestion into normalized `Evidence` and `Signal`
- malformed CSV rejection
- missing required-column rejection
- provenance presence on every imported item
- stable ID behavior for repeated imports of unchanged rows
- no regression in Workspace rendering of imported evidence/signals

## Planned PHASE 4 work: provider gateway and semantic cache

### Intended outcome

Wrap existing model routing in cleaner abstractions without replacing working runtime behavior prematurely.

Tranche 2 should introduce:

- a provider gateway interface around current model calls
- a semantic cache interface
- config-driven routing hooks

It should not yet become an aggressive runtime rewrite.

### Likely files to change

- `mas/extensions/runtime.py`
- new runtime module, likely `mas/runtime/gateway.py`
- new cache interface or implementation, likely `mas/runtime/cache.py`
- `mas/llm_client.py`
- `mas/config.py`
- possibly `mas/orchestrator.py` only for small hook points
- documentation files under `docs/`
- new tests under `mas/tests/`

### Expected interfaces/modules

- `ProviderGateway`
- `GatewayRequest`
- `GatewayResponse`
- `SemanticCache`
- `RoutingConfig`

Planned responsibilities:

- gateway chooses provider/model using config
- gateway exposes uniform latency/token/cost metadata
- cache is optional and interface-first
- routing config remains declarative and phase-aware

### Main design risks

- accidental behavior drift in working classify/hypotheses/strategy calls
- leaking provider-specific logic back into orchestration
- cache keys that are too broad or too narrow
- incorrect metrics if gateway and legacy usage accounting diverge

### Tests to run

- gateway chooses configured provider/model correctly
- fallback behavior remains intact
- cache interface can be disabled without changing outputs
- routing hooks respect config and do not bypass policy
- token/cost/latency metrics remain available
- no regression in existing parser/schema-repair paths

## What remains deferred after tranche 2

Still deferred:

- broad connector rollout beyond CSV
- spreadsheet, document, CRM, and SQL live integrations
- live external write actions
- approval-executed action flows
- vertical pack behavior beyond scaffolding
- normalized SQL-first persistence
- scenario authoring and multi-decision branching
- always-on monitoring runtime

## Suggested execution order

1. Land CSV normalization contract and tests
2. Add one CSV connector implementation behind the existing registry
3. Add provider gateway interface and adapter around current `llm_client`
4. Add semantic cache interface with a minimal non-invasive implementation or stub
5. Add config-driven routing hooks
6. Run regression suite plus focused ingestion/runtime tests

## Review boundary for tranche 2

If tranche-2 work requires:

- a persistence-model rewrite
- policy relocation into the LLM layer
- open-ended autonomous actions
- broad API redesign

the work should stop and be re-planned instead of forced through.
