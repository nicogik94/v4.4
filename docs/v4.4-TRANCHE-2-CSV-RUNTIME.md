# v4.4 Tranche 2 — CSV Connector and Runtime Layer

This document describes the tranche-2 additions that landed on top of the tranche-1 baseline.

Scope implemented in tranche 2:

- one real CSV connector
- normalized CSV import into `Evidence` and `Signal`
- provenance for imported records
- provider gateway abstraction
- semantic cache interface with safe default behavior
- config-driven routing hooks

Still deferred:

- connectors beyond CSV
- live external write actions
- multi-scenario authoring
- broad runtime replacement
- cache-backed decision shortcuts

Authoritative verification environment:

- `docker compose -f mas/docker-compose.yml`
- primary service: `app`

Verification posture:

- CSV connector tests run fully offline
- provider gateway tests use mocks/stubs by default
- no real provider credentials are required for tranche-2 verification
- live API smoke was run against the local compose app

## CSV connector overview

### Route

Additive route:

- `POST /projects/{id}/imports/csv`

This route does not replace any existing project or phase routes.

### Request shape

Current JSON request fields:

- `filename`
- `csv_text`
- `mapping`
- `actor`
- `dry_run`
- `source_ref` optional

This tranche uses JSON body import instead of multipart upload so the feature works without adding a new upload stack.

### Mapping contract

Each mapping rule supports:

- `column`
- `target_type`: `evidence | signal | ignore`
- `target_field`
- `value_type`: `string | number | boolean | datetime | category`
- `required`
- `transform`
- `signal_kind`
- `confidence`
- `drop_if_empty`
- `default_value`

Current supported target fields:

- Evidence:
  - `title`
  - `summary`
  - `category`
  - `linked_hypothesis_ids`
  - `linked_risk_ids`
- Signal:
  - `name`
  - `description`
  - `cadence`
  - `kind`
  - `confidence`
  - `linked_hypothesis_ids`

Unknown CSV columns are ignored but reported in the import summary.

### Default mapping example

```json
{
  "filename": "seo-signals.csv",
  "actor": "operator",
  "dry_run": false,
  "csv_text": "hypothesis_id,evidence_title,evidence_summary,signal_name,signal_description\nH1,CTR evidence,Search demand is rising,CTR,Weekly CTR movement\n",
  "mapping": [
    {"column": "hypothesis_id", "target_type": "evidence", "target_field": "linked_hypothesis_ids"},
    {"column": "evidence_title", "target_type": "evidence", "target_field": "title", "required": true, "transform": ["trim"]},
    {"column": "evidence_summary", "target_type": "evidence", "target_field": "summary", "transform": ["trim"]},
    {"column": "signal_name", "target_type": "signal", "target_field": "name", "required": true, "signal_kind": "performance", "confidence": 0.8},
    {"column": "signal_description", "target_type": "signal", "target_field": "description"},
    {"column": "hypothesis_id", "target_type": "signal", "target_field": "linked_hypothesis_ids"}
  ]
}
```

### Import behavior

Current behavior:

- header-based parsing
- row-level validation
- partial row failure is allowed
- one row may create `Evidence`, `Signal`, or both
- repeated imports dedupe exact records by stable ID when merged into canonical import storage

Dry-run behavior:

- validates and normalizes
- returns import summary
- does not persist imported records

Persisted behavior:

- stores normalized imported records in canonical `ProjectState` import fields
- rebuilds `decision_objects`
- makes imported evidence/signals visible in Workspace-derived views

### Provenance for imports

Every imported `Evidence` and `Signal` includes:

- `source_type = connector_import`
- `source_ref = <filename>#row=<n>`
- `captured_at`
- `captured_by`
- `connector = csv`
- `external_uri = <filename>`
- `checksum = <sha256 row fingerprint>`

Additional provenance note currently includes:

- file SHA-256 hash
- `untrusted_source=true`

### Untrusted-data handling

CSV content is treated as untrusted data.

Current safety rules:

- imported CSV text is not treated as instructions
- imported records stay in data objects and decision objects; tranche 2 does not wire raw CSV text into system prompts
- free-text fields are truncated before storage in import-derived `Evidence` and `Signal`
- imported `Evidence` and `Signal` are flagged as `untrusted_source = true`
- raw CSV rows are not dumped into logs

### Workspace effect

Imported records are merged into canonical import storage on `ProjectState`.

`decision_objects` then derives from:

- phase outputs
- imported evidence
- imported signals

As a result, imported records show up in existing Workspace panels such as:

- evidence timeline
- signal counts within decision object health
- any linked hypothesis evidence counts when linked IDs are supplied

### Imported evidence and reruns

Imported evidence and signals are canonical additive inputs.

Current product contract:

- imported evidence/signals appear immediately in `ProjectState`
- imported evidence/signals appear immediately in the derived `decision_objects` layer
- imported evidence/signals appear immediately in Workspace views such as evidence timeline and signal counts
- imported evidence/signals do **not** automatically invalidate or recompute prior phase outputs
- imported evidence/signals do **not** silently rerun analysis
- a rerun is required before imported evidence/signals can change downstream analysis or recommendations

Workspace now exposes a separate backend-computed operational notice when imported evidence exists after prior analysis/report outputs were already present:

- `imported_evidence_pending_analysis`
- `imported_evidence_pending_phase`
- `imported_evidence_pending_message`

Important semantic note:

- `decision_objects.status = fresh` means the derived decision-object layer is synchronized with the current stored state
- it does **not** mean every newly imported external record has already changed prior LLM-generated analysis outputs
- the imported-evidence pending-analysis flag is the operator-facing signal for that distinction

## Runtime gateway overview

### Goal

`call_llm()` remains the compatibility entrypoint, but provider selection and cache hooks now sit behind a gateway abstraction.

This keeps current orchestration code stable while making future routing/caching work additive.

### Runtime pieces

Implemented modules:

- `mas/runtime/provider_gateway.py`
- `mas/runtime/cache.py`
- `mas/extensions/runtime.py`

Current runtime behavior:

- `call_llm()` still works as the public wrapper used by orchestration
- low-level Anthropic/OpenAI request functions remain in `llm_client.py`
- the gateway chooses model/provider from config and compatibility routing rules
- retry, fallback, and cross-provider fallback are preserved

### Cache behavior

Implemented caches:

- `NoOpSemanticCache`
- `InMemorySemanticCache`

Default behavior:

- cache disabled by default
- no-op cache path is safe and preserves current behavior
- cache is never required for correctness

Current cache key strategy:

- SHA-256 over normalized phase, routing context, provider/model, and prompt payload

### Runtime observability

The provider gateway now emits lightweight runtime summary logs for each call without dumping raw prompts or responses.

Current summary fields include:

- selected provider
- selected model
- final provider
- final model
- cache enabled/disabled
- cache status: `disabled | bypass | miss | hit`
- latency
- fallback used or not
- error type

### Routing hooks

Routing remains explainable and config-driven.

Current inputs:

- phase
- complexity hint
- explicit model override

Current default:

- phase-based routing from existing `MODEL_ROUTING`

### Config additions

Additive runtime config environment surface:

- `DEFAULT_PROVIDER`
- `ROUTING_STRATEGY`
- `SEMANTIC_CACHE_ENABLED`
- `SEMANTIC_CACHE_TTL_SECONDS`
- `PHASE_MODEL_OVERRIDES`
- `COMPLEXITY_MODEL_OVERRIDES`

These are additive. Existing local defaults continue to work without setting them.
