# v4.4 Explainability / Decision Trace Layer

This document describes the additive explainability layer added after tranche 3A.

Scope implemented:

- backend-derived per-phase trace summaries
- strategy evidence-chain explanations
- explicit separation between deterministic logic, model judgment, policy enforcement, runtime metadata, and knowledge-layer inputs
- uncertainty summaries
- additive API routes
- additive dashboard visibility

Not implemented:

- raw chain-of-thought
- raw prompt dumps as primary UX
- broad prompt-facing knowledge retrieval
- orchestration changes

## Design rule

The trace layer is derived from existing persisted artifacts.

It uses:

- `ProjectState`
- phase outputs
- `phase_summaries`
- `phase_confidence`
- deterministic gate results
- policy audit events
- runtime counters
- knowledge-layer status

It does not invent hidden reasoning and it does not expose raw chain-of-thought.

## API routes

Additive routes:

- `GET /projects/{id}/trace`
- `GET /projects/{id}/trace/{phase}`
- `GET /projects/{id}/explain`

### `/trace`

Returns one project-level trace with per-phase summaries:

- phase name
- purpose
- inputs used
- frameworks used
- output summary
- confidence
- gate result
- next step
- logic separation
- uncertainty

### `/trace/{phase}`

Returns the derived trace for one phase only.

### `/explain`

Returns the richer operator-facing explanation view:

- project overview
- all phase traces
- strategy evidence chains
- project-level uncertainty summary
- logic separation summary
- policy highlights
- runtime summary

## Explainability contract

The trace layer distinguishes:

- deterministic logic
- model judgment
- policy enforcement
- runtime metadata
- knowledge-layer inputs

Important:

- deterministic logic means things like gate checks, deterministic scores, counters, and status transitions
- model judgment means structured output text already persisted in phase outputs
- policy enforcement means audit-log and approval/kill-switch/breaker facts
- runtime metadata means persisted usage/counter facts, not hidden provider internals
- knowledge-layer inputs are shown as present/current/stale; in the current bounded slice, only audit and strategy may show retrieval-approved knowledge items that were actually used in prompt assembly
- if a phase is recorded as completed but a present-time deterministic gate recomputation differs, the trace reports the recorded completion outcome and marks that difference as a gate note instead of implying the workflow was blocked retrospectively

## Strategy evidence chains

For each strategy action, the explainability layer exposes:

- claim / recommendation
- justification
- evidence chain string from the strategy output
- supporting evidence objects linked through `decision_objects`
- supporting findings from verdicts / gauntlet / audit where available
- deterministic checks relevant to the recommendation
- confidence label and score
- uncertainty / open questions

## Uncertainty contract

Uncertainty is derived from existing state only.

Current sources include:

- hypotheses still open or needing monitoring
- missing linked evidence
- audit observation needs
- confirm/reject criteria that would change conclusions
- monitor canaries and monitoring plans

## Operator note

Use:

- **Workspace** to understand operational status
- **Trace** to understand how the system arrived at the current result
- **Dossier** to edit content

The Trace view is an explanation layer, not a hidden-reasoning dump.

When audit or strategy used retrieval-approved knowledge, Trace will show the specific approved knowledge items used. This is derived from audit/runtime artifacts, not from raw prompt dumps.

Trace may also show:

- whether retrieval was used for audit or strategy
- current eligible vs blocked counts for those phases
- concise blocked-reason summaries

Those fields are visibility metadata only. They do not claim that retrieval changed the final result in a quantified way.

Status axes remain separate here:

- `decision_objects.status` = whether the derived decision-object layer is synchronized with the current stored state
- `imported_evidence_pending_analysis` = whether imported evidence/signals exist but still require a successful rerun before they change downstream analysis outputs
- `knowledge_health` / `knowledge_status` = whether synced external knowledge is current, stale, expired, or failed, independently of decision-object freshness
