# v4.4 Tranche 1 Baseline

This document captures the accepted baseline after Decision-OS tranche 1.

Tranche 1 does two things:

1. Adds an additive `decision_objects` layer inside `ProjectState`
2. Adds a backend-computed Workspace view for operators and reviewers

It does not replace the existing phase-driven engine. Existing phase outputs remain the canonical editable source of truth.

## Operator note

- `Dossier` is the edit surface. Use it to update the brief, supporting data, and structured phase outputs.
- `Workspace` is the operational command center. Use it to understand current status, risks, evidence, approvals, stale downstream work, and what needs review.

## Decision object architecture

### Canonical source rule

In tranche 1, `decision_objects` is derived from current project state. It is not authoritative on its own.

Direction of truth:

- phase outputs -> `decision_objects`
- not `decision_objects` -> phase outputs

The canonical inputs remain:

- `brief`
- `data`
- `classify`
- `hypotheses`
- `gauntlet`
- `audit`
- `strategy`
- `monitor`
- `sqi`
- `det_scores`
- `report`
- approvals and relevant policy/audit state
- re-entry history and outcome/calibration fields

### State models

`mas/state.py` now includes an additive `decision_objects` container with these submodels:

- `Provenance`
- `Decision`
- `Evidence`
- `Risk`
- `DecisionAction`
- `Signal`
- `ApprovalRecord`
- `OutcomeLink`
- `CalibrationSnapshot`
- `DecisionObjects`

`Hypothesis` also has additive `evidence_ids` so the hypothesis table can link back to derived evidence.

### One primary decision per project

Tranche 1 assumes one primary decision per project. The model is future-compatible with multiple scenarios later, but the current builder creates one primary `Decision`.

### Current mapping rules

The deterministic builder in `mas/decision_objects.py` maps state into decision objects as follows:

- `classify` -> primary `Decision` shell and summary framing
- `hypotheses` -> linked decision hypotheses and hypothesis-originated `Signal` objects
- `gauntlet` -> `Risk` objects plus linked `Evidence`
- `audit` -> `Risk` objects plus linked `Evidence`
- `strategy.strategies` -> `DecisionAction` objects
- `monitor` -> `Signal` objects from monitoring schedule, canaries, and circuit breakers
- `approvals_granted` and approval-related policy events -> `ApprovalRecord`
- predictions / calibration fields -> `OutcomeLink` and `CalibrationSnapshot`

### Rebuild triggers

The system rebuilds or refreshes `decision_objects` in these paths:

- project create
- store load and list operations
- phase completion
- workflow resume / re-entry invalidation
- operator dossier edits
- risk-classification changes
- approval changes
- workspace and state reads when the snapshot is missing or stale

The rebuild path is centralized in `ensure_decision_objects(...)`.

## Stable ID rules

Stable IDs are required so linked objects do not reshuffle across rebuilds when the underlying semantics have not changed.

### Object ID generation

`mas/decision_objects.py` uses:

- `stable_object_id(kind, *parts)`

Rules:

- IDs are semantic, not positional
- normalized source parts are joined and hashed
- the current implementation uses a SHA-1 digest truncated to 12 hex characters
- the returned ID is prefixed by object type, for example `risk_<digest>` or `evidence_<digest>`

### Current semantic inputs

Examples of current ID material:

- decision: project id + `"primary"`
- hypothesis-linked signal: project id + hypothesis id + signal text
- gauntlet risk: project id + result id + crux / top FMEA / rank
- audit risk: project id + FMEA component + failure mode + effect + RPN
- evidence: project id + source section + source reference + normalized finding text
- action: project id + action text + framework source + priority

The exact implementation lives in `mas/decision_objects.py`. If the semantic source changes materially, the ID may change. Cosmetic reordering should not.

### Source state hash

The freshness contract is driven by:

- `compute_source_state_hash(state)`

Rules:

- the hash is computed from the subset of `ProjectState` that feeds decision-object derivation
- derived fields such as `Hypothesis.evidence_ids` are intentionally excluded from the hash input
- the current implementation uses SHA-256 over a normalized JSON payload

## Decision object lifecycle

`DecisionObjects.status` supports three states:

- `fresh`
- `stale`
- `rebuild_failed`

### `fresh`

`decision_objects` is `fresh` when:

- the object graph rebuilt successfully
- `source_state_hash` matches the current hash
- the latest rebuild metadata is recorded

Required metadata on a fresh snapshot:

- `schema_version`
- `rebuilt_at`
- `source_state_hash`
- `status = fresh`

### `stale`

`decision_objects` becomes `stale` when:

- the source state has changed since the last good rebuild
- downstream invalidation or operator edits altered upstream canonical inputs

Important:

- `stale` means "needs rebuild or review", not "missing"
- Workspace surfaces must treat stale state explicitly

### `rebuild_failed`

`decision_objects` becomes `rebuild_failed` when:

- the rebuild path throws an exception

Current behavior:

- the snapshot preserves failure metadata
- `rebuild_error` stores the message
- the failure is surfaced in Workspace
- a policy audit event is attempted so the failure is traceable

## Provenance rules

`Evidence` and `Signal` require `Provenance`.

Required fields:

- `source_type`
- `source_ref`
- `captured_at`
- `captured_by`

Optional fields:

- `connector`
- `external_uri`
- `checksum`
- `notes`

Current source-type conventions:

- `phase_output`
- `connector_import`
- `operator_edit`
- `system_derived`

## Backend-authoritative Workspace contract

Workspace status is computed in the backend. The frontend may style and group it, but it must not re-derive workflow meaning.

The backend summary model is `WorkspaceSummary` in `mas/workspace.py`.

### Authoritative fields

- `project_status`
- `phase_statuses`
- `blocking_reasons`
- `requires_approval`
- `has_stale_downstream`
- `active_risk_count`
- `last_reentry_at`
- `score_summary`
- `decision_object_health`
- `active_risks`
- `evidence_timeline`
- `hypothesis_table`
- `approvals_panel`
- `reentry_history`

### `project_status` values

Current backend-computed statuses:

- `blocked`
- `review_required`
- `stale`
- `safe_to_proceed`
- `completed`

Decision rule summary:

- `blocked` if kill switch, failed phase, open breaker, or decision-object rebuild failure exists
- `review_required` if approvals are pending
- `stale` if downstream state or decision objects are stale
- `completed` if report is complete and present
- otherwise `safe_to_proceed`

### Decision object health

`decision_object_health` reports:

- lifecycle status
- schema version
- rebuilt timestamp
- source hash
- current hash
- rebuild error
- counts for decisions, evidence, risks, actions, signals, and approvals

This is the authoritative health signal for Workspace panels that depend on derived objects.

## API reference

### `GET /projects/queue`

Purpose:

- returns the operator queue for all projects using backend-computed status

Response model:

- `QueueItem[]`

Current fields:

- `project_id`
- `project_name`
- `current_phase`
- `project_status`
- `workflow_running`
- `blocking_reasons`
- `requires_approval`
- `has_stale_downstream`
- `active_risk_count`
- `decision_object_status`
- `sqi_overall`
- `brier_score`
- `updated_at`

Usage note:

- the dashboard project list should read from this endpoint, not infer queue state from raw project snapshots

### `GET /projects/{id}/workspace`

Purpose:

- returns the full backend-computed Workspace view for a single project

Response model:

- `WorkspaceSummary`

Usage note:

- the dashboard Workspace subtab should render directly from this response
- frontend logic may sort or format panels, but it should not recompute `blocked`, `review_required`, `stale`, `safe_to_proceed`, or `completed`

## Review boundary

This baseline is intentionally limited:

- no new write-side connectors
- no provider-gateway cutover
- no safe-action execution
- no pack-specific behavior
- no persistence migration

Those items remain deferred to later tranches.
