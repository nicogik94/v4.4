# R2.0A-4C — Evidence-Only Source Snapshot Ingress

Chain: R2.0A-1 → R2.0A-2 → R2.0A-3 → R2.0A-4A → R2.0A-4B → **R2.0A-4C**.

This wave closes exactly one missing ingress capability: an authenticated local
operator can create canonical v47 `SourceBlob` + `SourceSnapshot` records from
**operator-supplied immutable local bytes**, without passing through Knowledge
ingestion and without creating or mutating Knowledge sources, Knowledge items,
uploaded-file manifests, `ProjectState` Knowledge, `imported_evidence`, or
`imported_signals`.

It adds ONE production service, ONE storage helper, and ONE bridge write command,
plus (from the audit remediation below) the mechanical provenance disclosure that
makes an evidence-only source distinguishable everywhere it is consumed.
It adds **no migration** and **no API route**.

## Discovery decision

| Claim | Verdict | Verification |
|---|---|---|
| the existing v47 schema can represent evidence-only capture with no schema change | **CONFIRMED** | `source_blob`, `source_snapshot`, `ingest_operation` are project-scoped; `source_kind`, `source_locator`, `storage_ref` are free-form `TEXT NOT NULL DEFAULT ''` with no CHECK constraint restricting them to upload semantics (`sql/v47_evidence_snapshot_foundation.sql`). |
| `CandidateFactRevision` requires an existing same-project `SourceSnapshot` | **CONFIRMED** | `candidate_fact_revision.source_snapshot_id UUID NOT NULL` + composite FK `fk_cfr_snapshot_project → source_snapshot(id, project_id)`; the bounded `fact_service` additionally re-checks same-project existence and canonical availability. |

Capture there is a *side effect* of Knowledge ingestion. |
| no current validated public service or bridge command provides evidence-only ingress | **CONFIRMED** | `capture.capture_upload` is the upload-path seam (owns its own connection + COMMIT, derives `upload:<digest>` operation ids); `repository.insert_snapshot`/`insert_or_get_blob` are ungated low-level append seams with no project validation, no provenance vocabulary, and no proof that `storage_ref` names bytes that exist. ## Service boundary

```
knowledge.evidence_snapshot.source_service.capture_evidence_source_bytes(
    conn, *, project_id, content: bytes, source_kind, source_locator,
    operation_id, actor="", expected_sha256=None
) -> dict   # source_snapshot_id, source_blob_id, operation_id,
            # content_sha256, byte_size, source_kind, source_locator,
            # reused, bytes_persisted
```

The service:

- is inert unless `MAS_EVIDENCE_SNAPSHOT_ENABLED` is set (it writes v47 rows);
- requires genuine non-empty bytes within a configurable size bound;
- preserves caller transaction ownership exactly as `fact_service` does — rejects
  autocommit, requires an **explicitly pinned** READ COMMITTED level
  (`isolation_level=None` does not prove READ COMMITTED and is rejected),
  **verifies the live isolation** with `SHOW transaction_isolation`, wraps its
  writes in a savepoint, and **never commits**;
- creates exactly one `IngestOperation`, one `SourceBlob` (deduplicated per
  project by content identity), and one `SourceSnapshot`, through the existing
  `knowledge.evidence_snapshot.repository` seams;
- creates **no** Knowledge object, `ProjectState` change, imported
  evidence/signal, candidate fact, claim, authorization, or parallel evidence
  database, and performs no parsing, no network access, and no LLM call. Its
  import surface is closed to `config`, `.repository`, `.source_storage`.

Every semantic rejection — disabled feature, autocommit/isolation attribute,
**malformed project id**, empty or oversized bytes, untruthful provenance kind,
blank locator/operation id, `expected_sha256` mismatch — happens **before any SQL
and before any byte is stored**. The only statements preceding the storage write
are the live-isolation verification, the project-existence read, and the
idempotency probe; none mutates anything.

The project id is validated against the canonical 8-4-4-4-12 UUID shape before
any statement runs (audit MINOR-1). `projects.id` is a `uuid` column, so malformed
text reaching that comparison raises `invalid input syntax for type uuid` and
leaves the **caller's** transaction aborted — a failure the caller did not cause
and cannot recover from without a rollback. The accepted shape is exactly
`source_storage.is_canonical_uuid`, the one predicate the store itself uses for
the project path segment, so a project id can never be admitted by the service
and then rejected by storage (proved in PG: a rejected malformed id leaves the
same transaction usable, and a genuine capture then commits on it).

## Provenance modes

`source_kind` describes **how this system obtained the bytes**, which for this
path is always "an operator supplied local bytes". `source_locator` separately
carries the operator's assertion about where the material originally came from, so
a normalized operator-curated record never has to masquerade as a raw original
artifact.

The vocabulary is closed:

| Accepted | Meaning |
|---|---|
| `operator_curated_research_evidence_record` | a normalized, operator-authored evidence record (e.g. derived from a frozen admission artifact) |
| `operator_supplied_document` | a document artifact the operator supplied verbatim as local bytes |

| Refused | Why |
|---|---|
| `uploaded_file` | belongs to the Knowledge upload path, which really does create a manifest, registry entry and Knowledge items. This ingress creates none of them. |
| `raw_web_capture` | would assert that this system fetched the material from the network. This path performs no fetching whatsoever. |

Refusing the reserved kinds is what keeps provenance **truthful rather than
fabricated**: the CLI does not even offer them (argparse `choices` are read from
the service, so the two can never drift), and the service rejects them with a
message naming the reason.

Capture operation ids are namespaced `evidence-source:<operator-id>`, so an
evidence-only capture can never adopt — or be adopted by — the upload path's
`upload:<digest>` `ingest_operation` row.

### Provenance must survive to the point of use (audit MAJOR-1)

A closed, truthful vocabulary at ingress is worthless if the distinction is
dropped downstream. The independent audit demonstrated exactly that: a source
captured as `operator_curated_research_evidence_record` kept its `source_kind`
through the A-3 `internal_analysis` projection (the frozen disclosure policy both
**allows** and **requires** it for that scope) but the A-4A consumer dropped it
in two places — the model-facing block and the durable consumption attestation.
`citation_label`, `canonical_source_locator`, `publisher`, `author`,
`published_at`, `retrieved_at`, `declared_quality_tier` and
`declared_quality_rationale` therefore reached the model with **no mechanical
provenance distinction**: a normalized operator-authored record was
indistinguishable from a raw captured artifact.

`mas/research_evidence_context.py` now carries the projected category through
both boundaries:

| Boundary | Behaviour |
|---|---|
| model-facing block (`_render_block_body`) | every projected source emits `     source_kind: <value>` as the first line of its `SOURCES` entry, immediately after `S<n> source_snapshot_id=…` and before `citation_label`. Unconditional (the policy *requires* the field for this scope, so a conditional emission could only hide the distinction) and **verbatim** — nothing is derived, normalized, inferred, or rewritten. |
| durable identity (`ResearchEvidenceSourceIdentity`) | additive `source_kind: str = ""`, populated from the projection in `_attestation_from_projection`, emitted in `event_details()["sources"]`, and read back by `_impact_from_event_details` so the Decision Trace impact does not drop it one hop later. |

Backward compatibility is structural, not incidental: the new field is additive
with a safe default, so attestations and `policy_audit_log` events recorded before
it existed still parse and simply report an empty category. **No migration, no
schema change, and no historical row is modified** — the attestation is a Pydantic
model persisted inside `ProjectState.policy_audit_log`, and `source_kind` was
already a v47 `source_snapshot` column carried by A-2/A-3.

What deliberately did **not** change: the frozen A-3 disclosure policy (and
therefore its fingerprint), the 65,536-byte consumer budget, the fail-closed
overflow behaviour, and the consumer-input allowlist — `storage_ref` is not a
projection field at all, and the private capture `source_locator`, blob ids and
metadata revision ids remain omitted. Scopes the policy does not authorize for
`source_kind` still have it omitted by A-3 before the consumer ever sees a
projection, and the consumer still refuses any non-`internal_analysis` projection.

## Storage semantics

`knowledge.evidence_snapshot.source_storage` owns a **dedicated, immutable,
content-addressed** store rooted at `config.evidence_source_storage_dir()`
(`MAS_EVIDENCE_SOURCE_STORAGE_DIR`, default `mas/evidence_source_store`). It is
deliberately **not** `UPLOAD_LAYER.storage_dir`: sharing the Knowledge upload root
would make an evidence-only blob indistinguishable from an upload's backing file
and couple this path to upload lifecycle behaviour it does not participate in.

```
<root>/<project_id>/sha256/<digest[:2]>/<digest>
```

- **content-addressed** — deterministic and collision-safe; project-scoped
  because v47 deduplicates blob content identity per project, so bytes are never
  shared across project boundaries by the store either;
- **traversal-safe** — the project id must match a UUID pattern and the digest 64
  lowercase hex characters, so no caller-supplied value can become an arbitrary
  path segment; the resolved target is additionally proven to stay inside the
  resolved root; a relative or empty root is refused;
- **atomic** — written to a temporary file in the destination directory, flushed,
  `fsync`-ed, then `os.replace`-d into place, with a directory `fsync` after the
  rename; a reader never observes a partial artifact;
- **verified** — re-read and re-hashed **from the final path** after the write; a
  mismatch is a hard failure and the reference is not returned;
- **immutable** — an existing reference is never overwritten. Matching bytes make
  the write a verified no-op (this is what makes a retry safe); *different* bytes
  raise `EvidenceSourceImmutabilityError` instead of replacing them;
- **owner-only** — every reference the store returns names a file at mode `0600`.
  A fresh write is restricted by construction (`tempfile.mkstemp` creates the
  incoming file `0600` and `os.replace` preserves it); an artifact that was
  *already* present is brought to `0600` before it is accepted, without touching
  its bytes. A file that is already restricted is left alone, and a genuine
  failure to restrict is a bounded `EvidenceSourceStorageError` rather than a
  silent accept.

`storage_ref` therefore always names bytes that genuinely exist. Errors are
bounded and never echo source content; the bridge never emits the reference.

`MAS_EVIDENCE_SOURCE_MAX_BYTES` is **fail-closed**: unset (or blank) means the
documented 5 MB default, an integer is honoured (clamped up to the intentional
lower bound of 1 byte, never down to 0), and anything else raises
`config.EvidenceSourceConfigurationError`. A malformed bound must not silently
become the *larger* default, which would admit an artifact the operator meant to
exclude; the bridge surfaces the bounded message and refuses the capture.

## Transaction / failure semantics

A POSIX filesystem and PostgreSQL cannot participate in one atomic transaction,
and this wave does not pretend otherwise. The ordering is deliberate and
one-directional:

1. bytes are made durable and digest-verified on disk;
2. only then are the `IngestOperation` / `SourceBlob` / `SourceSnapshot` rows
   created on the caller's transaction.

| Failure | Outcome |
|---|---|
| storage fails | no row is created at all — not even the `IngestOperation` (proved in PG). |
| the database fails after the bytes land | nothing is committed. An **unreferenced** immutable blob may remain on disk; it is content-addressed, so a later genuine capture of the same bytes reuses rather than duplicates it, and it is unreachable as evidence because no snapshot references it (proved in PG). |
| dry-run (the bridge default) | commits **no** database state, but the bytes *are* written. A dry run is a genuine storage rehearsal: a dry run that "succeeded" while storage would have failed at commit time would be a lie. `source_bytes_persisted` and `source_bytes_retained_on_rollback` report this in the payload, and `source-capture --help` states it (see the bridge section). |

A **committed** `SourceSnapshot` can never point at absent or corrupt bytes. The
service asserts the reference's durability again before returning, and on an
idempotent retry it re-verifies the stored bytes and raises
`EvidenceSourceCaptureStorageMissing` rather than hand back a snapshot whose bytes
can no longer be verified.

## Orphaned evidence bytes — operator procedure

This wave ships **no garbage collector** and no cleanup subsystem, deliberately:
deleting evidence bytes is the one filesystem operation that can break the
durability guarantee above, so it stays a human, audited decision. What is
provided is a bounded identification rule.

**Definition.** A stored artifact at path `P` under the evidence source store is
*referenced* exactly when some `source_snapshot` row names it:

```sql
-- Is this artifact referenced by any snapshot? (run read-only)
SELECT count(*) FROM source_snapshot WHERE storage_ref = :P;
```

`count = 0` ⇒ **orphan candidate**. `count > 0` ⇒ **referenced evidence — never
delete it.** The reference is exact and content-addressed (no prefix matching, no
globbing, no digest recomputation is needed to decide this), and it is
project-scoped by construction: the project id is a path segment, so an artifact
under `<root>/<project_id>/…` can only ever be referenced by that project's
snapshots.

**Rules.**

1. **Never delete referenced bytes.** A committed `SourceSnapshot` whose bytes are
   absent breaks the wave's central guarantee; the service will refuse to reuse
   such a snapshot (`EvidenceSourceCaptureStorageMissing`) and the evidence
   becomes unverifiable rather than merely unavailable.
2. Only an artifact with **zero** referencing snapshots is a candidate, and only
   when the count is taken with **all capture transactions settled** — a capture
   in flight has already written its bytes and has not yet committed its snapshot
   row, so a concurrent sweep would classify live bytes as an orphan. Take the
   census while no capture is running.
3. Orphans are **harmless if left alone**: they are unreachable as evidence (no
   snapshot references them), they are content-addressed rather than
   ever-growing per retry, and a later genuine capture of the same bytes reuses
   them instead of duplicating them. Retention, not deletion, is the safe default.
4. Anything under the store that is not a regular file at
   `<root>/<project_id>/sha256/<digest[:2]>/<digest>` — or a leftover
   `.incoming-*.tmp` from an interrupted atomic write — was not produced by this
   store's normal operation and should be investigated, not swept.

**Diagnostics that already exist** (no new subsystem):
`source_storage.stored_bytes_present(storage_ref, expected_sha256=…)` answers
"are the bytes for this reference present and intact?", and
`source_storage.storage_reference(project_id, digest)` recomputes the canonical
reference for a known digest. Both are read-only. The bridge deliberately does
**not** emit `storage_ref`, so the census above is a server-side operator/DBA
procedure, not a CLI capability.

## Idempotency

Keyed on `(project_id, evidence-source:<operation_id>)`.

| Case | Behaviour |
|---|---|
| same operation id + same bytes + same metadata | returns the **existing committed** snapshot (`capture_reused: true`); no second row, no re-write. |
| same operation id + different bytes | `EvidenceSourceCaptureConflict` — "different source bytes; a capture event is immutable". |
| same operation id + materially different `source_kind`/`source_locator` | `EvidenceSourceCaptureConflict` — "different source metadata". |
| **new** operation id + same bytes | `SourceBlob` deduplicates; a **distinct immutable** `SourceSnapshot` is appended — one capture event per operation, consistent with v47. |
| operation marked committed with no snapshot | fails closed rather than appending a second capture under one operation identity. |

The mismatch check runs *before* the storage write, so a rejected retry leaves no
bytes behind. Append-only guarantees are untouched: the v47 `BEFORE UPDATE|DELETE`
triggers still reject mutation of the created rows (proved in PG).

That retry contract rests on `uq_ingest_operation_project_op`. At READ COMMITTED
two concurrent captures can both observe "no such operation"; only the UNIQUE
constraint forces the second writer to see the first operation. It is therefore
frozen as a catalog fact in the bridge's write preflight
(`CATALOG_CAPTURE_CONSTRAINTS`, folded into the same `constraints_ready` verdict),
cross-checked against the ratified v47 migration text by a static test.

## Bridge command

```
source-capture
  --project-id            (required)
  --file                  (required)  local filesystem path — never a URL
  --source-kind           (required)  choices read from the service vocabulary
  --source-locator        (required)
  --actor                 (required)
  --operation-id          (required)  stable idempotent retry key
  --expected-sha256       (optional)  binds the intended artifact
  --commit                            default is dry-run / rollback
  --expect-runtime-fingerprint (required for the write)
```

It requires **both** `MAS_RESEARCH_EVIDENCE_ENABLED` (it is a Research Evidence
bridge write) and `MAS_EVIDENCE_SNAPSHOT_ENABLED` (it touches v47 capture) —
`_run_write(..., requires_snapshot_flag=True)`; requires an explicitly configured
`DATABASE_URL`; uses one caller-owned non-autocommit READ COMMITTED transaction;
runs the existing fail-closed catalog-exact topology preflight and the pinned
runtime fingerprint; and persists only with `--commit`.

`--expected-sha256` is compared against the file's actual digest **in the command
body, before the connection is opened** — a mismatch fails before any storage
write and any SQL. The same value is passed through to the service so a direct
service caller gets the identical binding guarantee.

The command reads **local bytes only**. There is no URL input, no HTTP client, and
no network access; a pasted URL (`http://`, `https://`, `file://`, `s3://`, …) is
refused with an explicit "this command never fetches" message rather than being
treated as a filename.

Emitted JSON is metadata-safe: identities (`source_snapshot_id`,
`source_blob_id`, `capture_operation_id`), content identity (`content_sha256`,
`byte_size`), the provenance **category** (`source_kind` — the same safe label
`source-list` and the Automation-ROI workspace already expose), plus
`source_locator_recorded`, `capture_reused`, `source_bytes_persisted` and
`source_bytes_retained_on_rollback`.

### Dry-run scope is stated in the command's own help (audit MINOR-2)

`--commit` governs **database state only**. The storage-before-database ordering is
intentional and is *not* made side-effect-free: a dry run that "passed" while
storage would have failed at commit time would be a lie. What the audit required
instead is that the contract be unmistakable at the point of use, so
`source-capture --help` states in its own description that a dry run (or a
rolled-back/failed write) commits no database state while the **verified immutable
source bytes may remain in the evidence source store**, unreferenced by any
snapshot, and points at the orphan procedure above. The payload says the same
thing twice — `source_bytes_persisted` (preserved) and
`source_bytes_retained_on_rollback` — and the shared `--commit` help text for every
other bridge write command is untouched.

The private `storage_ref`, the operator's local file path, the source bytes, and
the **raw capture `source_locator`** are never emitted — the last of these keeps
the tool's existing posture (raw capture locators are private; only the
operator-declared `canonical_source_locator` on the metadata sidecar is a
reportable citation identity). `source_locator_recorded` confirms persistence
without reprinting the value.

No API route was added.

## Knowledge non-mutation proof

- the service's import surface is closed and contains no Knowledge module
  (asserted by AST, not substring matching, so the module may *describe* what it
  refuses to create);
- `knowledge/files.py` and `knowledge/evidence_snapshot/capture.py` are unchanged
  and do not know this ingress exists; the upload path still performs its own
  Knowledge work and its own `capture_upload`;
- in PG, after a committed evidence-only capture the `state_snapshots` relation —
  where `ProjectState` (and therefore the Knowledge layer, uploaded-file
  manifests, `imported_evidence` and `imported_signals`) is persisted — **does not
  exist at all**, let alone hold a row;
- the evidence store holds exactly one file (the raw bytes) and no manifest or
  parsed artifact; the Knowledge upload store is never created;
- the full canonical chain through `authorize-internal-analysis` completes with
  zero Knowledge objects for that source.

## D001R-shaped functional probe

On a **disposable project in a disposable database only** (no CACOFÓNICO project
id, no D001R database, no production compose), the complete canonical chain is
reachable from an evidence-only local file:

```
source-capture → source-list → source-metadata-create → fact-create
  → intake-create ×2 → intake-item-create ×2 → review-record ×2
  → claim-support-record → annotation-record → context-record
  → authorize-internal-analysis
```

and the canonical A-2 pack then contains the evidence-only source
(`claim_count == source_count == relationship_count == 1`, `source_kind ==
operator_curated_research_evidence_record`) while `state_snapshots` still does not
exist and the only `ingest_operation` is `evidence-source:probe-<tag>`.

This is a capability probe only. No audit/strategy phase and no LLM consumer was
executed.

## Accepted residual risks (deferred by the remediation scope)

Two audit Minors were confirmed as genuine and deliberately **not** fixed in this
wave, because each smallest safe fix is larger than the remediation's bounded
scope. They are recorded here rather than closed silently.

| Finding | Status | Accepted risk | Smallest future hardening |
|---|---|---|---|
| **MINOR-3** — symlink/TOCTOU in the store tree | valid as a genuine race only, deferred | `persist_source_bytes()` re-derives the reference through `storage_reference()`, so its realpath containment proof runs again on every write: a symlink planted at an intermediate directory (e.g. `<root>/<project>/sha256`) **before** the call is refused ("refusing a storage reference outside the configured store root"), and a symlink at the final component is replaced by `os.replace` (rename does not follow links) or fails the digest comparison. What remains is the window **between** that proof and the subsequent `mkdir`/`mkstemp`/`os.replace`: an attacker who wins it can make the bytes land outside the root (reproduced only by forcing the interposition at the first filesystem call after the check). The precondition is write access to the server-side evidence store tree, which already implies the ability to tamper with stored evidence directly — and such tampering is detected by the digest verification on use. No new read access to evidence, no database reach. | Publish through directory file descriptors: `os.open(..., O_DIRECTORY \| O_NOFOLLOW)` walking one segment at a time, then `os.mkdir`/`mkstemp`/`os.replace` relative to the verified fd (`dir_fd=`), so no component can be substituted after it is checked. Alternatively verify each component with `os.lstat` + `stat.S_ISDIR` while holding the parent fd. |
| **MINOR-7** — `persist_source_bytes` does not independently enforce the service size bound | valid, deferred | Confirmed by direct call: with `MAS_EVIDENCE_SOURCE_MAX_BYTES=8` the helper stores a 4096-byte artifact, while `capture_evidence_source_bytes` rejects the same content before any SQL and before any byte is written. The size bound lives in the service (and again in the bridge's `--file` reader), so the storage helper will write bytes of any length if called directly. Every production path goes through the service, and the helper is not exported to any endpoint, CLI, or Knowledge caller; the risk is a *future* direct caller bypassing the bound, not a current one. | Add a `max_bytes` keyword to `persist_source_bytes` that defaults to `config.evidence_source_max_bytes()` and rejects oversized content before `mkstemp`, so the bound holds even for a direct caller. Deferred because it duplicates a validated bound and its error class differs (`EvidenceSourceStorageError` vs `EvidenceSourceCaptureValidationError`), which changes the service's documented pre-SQL rejection story. |

## Out of scope / unchanged

No migration (v62 stays unused). No API route, no UI, no web crawling, no HTTP
download, no live research, no new Research Evidence consumer. The A-3 disclosure
policy and its fingerprint, the 65,536-byte budget, fail-closed overflow, pack
eligibility, authorization semantics, usage scopes, audit/strategy phase
eligibility, workflow execution, model routing, and historical migrations are
untouched. The A-4A consumer changed only by *carrying through* the provenance
category A-3 already discloses (see MAJOR-1 above) — it added no field to the
projection, widened no scope, and admitted no new persistence mechanic. Knowledge
upload behaviour is unchanged. Feature-off behaviour is unchanged (writes fail
closed).
