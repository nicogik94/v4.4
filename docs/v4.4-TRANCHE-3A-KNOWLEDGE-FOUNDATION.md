# v4.4 Tranche 3A — Knowledge Foundation

This document describes the tranche-3A current-awareness foundation that landed on top of tranche 2.

Scope implemented in tranche 3A:

- additive `knowledge_layer` state inside `ProjectState`
- source registry entries
- knowledge items
- freshness policies
- manual offline sync jobs and sync state
- backend-authoritative knowledge status in Workspace and Queue
- additive API routes for knowledge read/sync flows

Still deferred:

- prompt-facing retrieval
- projection of knowledge into LLM reasoning
- automatic orchestration reruns or invalidation
- live external source connectors
- scheduled sync workers

## Core architecture rule

`ProjectState` remains canonical.

`knowledge_layer` is additive persisted state for source definitions, synced knowledge items, and sync history.

It is separate from:

- phase outputs
- `decision_objects`
- orchestration status

Important semantic boundary:

- `decision_objects.status` still means the derived decision-object layer is synchronized with the current canonical phase/import state
- `knowledge_health.status` is a separate operational signal for current-awareness freshness
- `imported_evidence_pending_analysis` is a third signal: imported evidence/signals are present in state, but a successful rerun has not yet incorporated them into downstream analysis outputs

Tranche 3A does not make knowledge items prompt-facing and does not change phase semantics.

Operator reading rule:

- `decision_objects.status = fresh` does **not** mean imported evidence already changed recommendations
- `knowledge_health.status = current` does **not** mean the knowledge layer is prompt-facing
- if imported evidence is pending analysis, rerun the relevant analysis/report path before treating outputs as updated

## State additions

`mas/state.py` adds:

- `knowledge_layer: KnowledgeLayerState | None`
- `SourceRegistryEntry`
- `KnowledgeItem`
- `FreshnessPolicy`
- `KnowledgeSyncJob`
- `KnowledgeSyncState`
- `KnowledgeLayerState`

### SourceRegistryEntry

Represents one configured knowledge source.

Current tranche-3A fields include:

- `source_id`
- `name`
- `source_kind`
- `connector_type`
- `owner`
- `domain_tags`
- `sensitivity`
- `trust_tier`
- `enabled`
- `access_mode`
- `freshness_policy_id`
- `secret_ref`
- sync metadata such as `last_sync_at`, `last_success_at`, `last_error`

No raw secrets are stored in `ProjectState`.

### KnowledgeItem

Represents one synced knowledge record.

Current fields include:

- `item_id`
- `source_id`
- `source_ref`
- `title`
- `summary`
- `structured_payload`
- `observed_at`
- `captured_at`
- `effective_at`
- `expires_at`
- `checksum_sha256`
- `provenance`
- `freshness_status`
- `trust_tier`
- `sensitivity`
- `untrusted_source`
- `eligible_for_retrieval`

In tranche 3A:

- `eligible_for_retrieval` is always `false`
- items are not used in prompts

With controlled retrieval added later, runtime eligibility is computed by the backend retrieval layer per phase. The persisted item model remains additive and is not itself the authoritative retrieval decision surface.

### FreshnessPolicy

Current tranche-3A policy fields:

- `policy_id`
- `name`
- `stale_after_hours`
- `expire_after_hours`
- `manual_review_required`
- `allow_stale_read`

Default policy:

- `default_offline`

### KnowledgeSyncJob / KnowledgeSyncState

`KnowledgeSyncJob` tracks one manual sync attempt:

- `job_id`
- `source_id`
- `requested_at`
- `completed_at`
- `requested_by`
- `status`
- `mode`
- inserted/updated/removed counts
- checksum/error fields

`KnowledgeSyncState` tracks the layer-level operational summary:

- `status`
- `last_sync_at`
- `last_success_at`
- `last_error`
- `last_job_id`
- `jobs`

## Offline/manual sync contract

Tranche 3A supports only manual offline sync.

Allowed today:

- operator registers an `offline_fixture` source
- operator posts fixture items to a sync route
- synced items are persisted in `knowledge_layer.items`
- Workspace and Queue expose knowledge freshness

Not allowed today:

- live network fetches by default
- scheduled background sync
- prompt injection of knowledge text into system/user prompts

## Fail-closed rules

Tranche 3A fails closed when:

- source is disabled
- source is not `offline_fixture`
- source is not `manual`
- source sensitivity is not `public` or `internal`

Sensitive sources remain blocked until a later tranche adds explicit policy and access handling.

## API routes

Additive routes:

- `GET /projects/{id}/knowledge`
- `GET /projects/{id}/knowledge/sources`
- `GET /projects/{id}/knowledge/jobs`
- `POST /projects/{id}/knowledge/sources`
- `POST /projects/{id}/knowledge/sync`
- `POST /projects/{id}/knowledge/sync/{source_id}`

### `GET /projects/{id}/knowledge`

Returns:

- `project_id`
- backend-computed knowledge `summary`
- current persisted `knowledge_layer`

### `POST /projects/{id}/knowledge/sources`

Registers or updates one source registry entry.

Current intended use:

- register an `offline_fixture` source for manual sync smoke and operator-driven current-awareness inputs

### `POST /projects/{id}/knowledge/sync/{source_id}`

Manual offline sync of one registered source.

Current body contains:

- `actor`
- `items`

Each item includes:

- `source_ref`
- `title`
- `summary`
- `structured_payload`
- `observed_at`
- `effective_at`
- `expires_at`
- `trust_tier`
- `sensitivity`

## Workspace and Queue status

Workspace and Queue now expose knowledge freshness separately from project and decision-object status.

Current knowledge status values:

- `unconfigured`
- `current`
- `stale`
- `expired`
- `sync_failed`

This status is backend-computed from:

- configured sources
- source sync timestamps/errors
- item freshness windows
- current freshness policy

It does not trigger orchestration behavior by itself.

## What tranche 3A does not do

Tranche 3A intentionally does not:

- change `decision_objects` semantics
- alter orchestration or rerun behavior
- invalidate phases automatically
- expose knowledge items to prompt assembly
- require live external services

That work belongs to tranche 3B or later.
