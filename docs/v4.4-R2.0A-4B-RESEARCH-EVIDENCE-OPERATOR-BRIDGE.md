# R2.0A-4B — Research Evidence Operator Bridge

Chain: R2.0A-1 → R2.0A-2 → R2.0A-3 → R2.0A-4A → **R2.0A-4B**.

This wave adds ONE bounded operator CLI (`mas/tools/research_evidence_bridge.py`)
that lets an authenticated local operator construct, inspect, authorize, revoke,
and preview canonical Research Evidence using the existing v47 (Slice A) and
v51–v61 (Research Evidence) architecture. It exists to make the future
CACOFÓNICO D001‑v1 validation possible:

```
same decision + same Knowledge + explicitly authorized Research Evidence
  → audit/strategy → compare against D001‑v0
```

The bridge **consumes and drives existing services**. It creates no parallel
evidence system, adds no migration (v62 stays unused), performs no raw SQL
writes as a production contract, and enables no feature flag by itself.

## Ownership boundaries (unchanged from A‑1…A‑4A)

- **A‑2** (`research_evidence.pack_service`) owns membership *and* authorization
  eligibility. The bridge never recreates or approximates the eligibility rules;
  `authorize-internal-analysis` calls `record_usage_authorization_decision` and
  lets A‑2 decide. Verified in code: eligibility requires a current claim
  annotation, the exact current eligible support assessment
  (`resolvable`/`linked`/`support|qualification`), current approved claim *and*
  evidence reviews, available endpoints with current lineage, and the pack
  capacity bounds — none of which the bridge re-implements.
- **A‑3** (`presentation_projection_service`) owns disclosure. Previews call the
  public A‑3 entry with `internal_analysis` fixed.
- **A‑4A** (`research_evidence_context`) owns consumption, the frozen
  65,536‑byte model‑facing budget, and the exact renderer. `projection-preview`
  **reuses** `render_research_evidence_block` read‑only; it does not re-derive
  the budget or renderer. `trace-inspect` **reads the persisted attestation**
  A‑4A already recorded (via `build_phase_research_evidence_impact`); it does not
  run the live consumer or simulate a fresh consumption.

## Candidate‑fact production‑service decision

**Decision: add the smallest bounded service wrapper**
`mas/knowledge/evidence_snapshot/fact_service.py::create_candidate_fact_revision`.

Discovery found **no existing validated public production service** that creates
a bare `candidate_fact_revision`:

- `knowledge.evidence_snapshot.repository.insert_fact` is a low‑level append seam
  (its own docstring: "narrow insert/read repository … deliberate typed
  callers"); no feature gate, no transaction‑ownership guard, no same‑project
  snapshot binding. Calling it directly from the CLI would be a raw repository
  bypass.
- `knowledge.automation_roi.repository.create_eligible_fact` reuses that seam but
  couples every fact to a Slice‑B `candidate_fact_extraction_context` row —
  Automation‑ROI‑specific storage, explicitly out of scope.
- `research_evidence.service.create_fact_metadata_revision` only attaches the
  R1.1 metadata sidecar to an *already existing* fact id.

The wrapper accepts a `ValidatedFact` but **never trusts it on type alone**:
`ValidatedFact` is a plain dataclass any caller can construct directly, bypassing
`validate_fact`. The service therefore reconstructs a canonical fact from every
field through the canonical `validate_fact` and persists **only** that canonical
result — a forged or internally inconsistent value (bad currency/date, missing
rate contexts, out‑of‑bounds percentage subtype, negative/invalid duration,
non‑integral count, blank text, unknown type) is rejected **before any SQL or
SAVEPOINT runs**. It binds the fact only to an existing, **same‑project**,
**canonically available** `source_snapshot`: after the same‑project existence
check it re‑uses the canonical v47 resolver
`knowledge.evidence_snapshot.repository.snapshot_available` — the exact boundary
Research Evidence intake enforces — so a `tombstone` or `redact` retention event
on the snapshot **or its underlying `source_blob`** blocks new fact creation with
`CandidateFactSourceSnapshotUnavailable` ("source snapshot is tombstoned or
redacted"), while `legal_hold` does **not** change availability. The existence
check stays separate from and ahead of the availability check — `snapshot_available`
is a `NOT EXISTS` resolver that reports a *non‑existent* snapshot as "available",
so a missing or foreign‑project snapshot continues to raise
`CandidateFactSourceSnapshotNotFound`, never the unavailable error. The
availability check runs inside the caller‑owned transaction/savepoint immediately
before the insert, adds no new locking protocol, and the bridge never reactivates
or repairs retained evidence. It
preserves caller transaction ownership (rejects autocommit and requires an
**explicitly pinned READ COMMITTED** level — `isolation_level=None` merely
delegates to the server default and does not prove READ COMMITTED, so it is
rejected, as are REPEATABLE READ / SERIALIZABLE; never commits, wraps its work in
a savepoint), uses the `repository.insert_fact` seam, adds no new storage, creates
no authorization, and never infers a fact from Knowledge. It has unit (including
forged‑instance and None‑isolation) and PostgreSQL tests (which pin READ COMMITTED
before invoking the service, as the bridge does), including retention coverage —
snapshot‑target and blob‑target `tombstone`/`redact` are rejected with zero new
facts, a `legal_hold` control still succeeds, and the real `fact-create` command
fails closed (non‑zero exit, `CandidateFactSourceSnapshotUnavailable`, no fact or
metadata persisted, retention state untouched, transaction rolled back).

The wrapper also rejects a **non‑finite numeric value** (`NaN`, `Infinity`,
`-Infinity`) for every numeric fact type (`money`, `rate`, `percentage`,
`duration`, `count`), with the canonical `FactValidationError` and the fixed,
non‑echoing message *"numeric candidate facts must be finite"*, **before any SQL
or SAVEPOINT runs**. This is required because PostgreSQL's own `NUMERIC` type
stores `NaN`/±`Infinity`, so persistence cannot be relied on to reject them, and
the canonical `validate_fact` does not universally reject them (`money`/`rate`
and the unbounded `percentage` `change` subtype admit any non‑finite value;
`count`/`duration` admit infinities). `Decimal.is_finite()` is the authoritative
check, applied both before and after `validate_fact` inside canonicalization so
the rejection is uniform even for the profiles whose bound comparisons would
otherwise raise a non‑canonical `decimal.InvalidOperation` on a `NaN`. Textual
facts are unaffected. This correction is bounded to the A‑4B wrapper; the
historical `validation.py` is not modified.

`preflight` intentionally does **not** model this: it is not a predictor of every
service‑level semantic validation. The safety property is that even when topology
preflight passes, `fact-create` itself fails closed before creating a fact from a
canonically unavailable source, or from a non‑finite numeric value.

## Invocation

The tool runs directly from the repository root, with no `PYTHONPATH` setup
required of the operator:

```
python mas/tools/research_evidence_bridge.py --help
python mas/tools/research_evidence_bridge.py preflight
```

A direct invocation puts `mas/tools` — not `mas` — at `sys.path[0]`, so the
script performs the same bounded bootstrap the repository's other tools
(`cdp_review`, `validate_t1a_gate2`) already use: it prepends the `mas` root,
derived from `__file__`, before importing any application module. No
environment‑specific absolute path is used and no import is weakened. A
subprocess test invokes the real script entrypoint from the repository root with
`PYTHONPATH` removed from the environment, proving both `--help` and a normal
`preflight` reach bridge execution rather than failing during imports.

## Write safety

Every write requires `MAS_RESEARCH_EVIDENCE_ENABLED=true` (and
`MAS_EVIDENCE_SNAPSHOT_ENABLED=true` for `fact-create`, which touches v47 facts),
runs on ONE caller‑owned, non‑autocommit, READ COMMITTED transaction, defaults to
rollback/dry‑run, and persists only with `--commit`. Validation or confirmation
failure emits no COMMIT and returns a non‑zero exit. Request‑ID–bearing writes
(review/freshness/claim‑support/annotation/context/authorization) are idempotent
on retry and reject a reused request ID with mismatched content (both proven at
the PG level). Partial historical records built by separate successful commands
are acceptable because the stores are append‑only; each individual command is
transactionally complete.

### Fail‑closed write preflight (enforced, not advisory)

`preflight` is a diagnostic; it does **not** stand in for enforcement. Every
write command runs the **same fail‑closed preflight on its own write connection
before any service write**, and any unmet prerequisite rolls back and returns
non‑zero (`BridgePreflightError`):

- **Explicit DATABASE_URL.** A write requires an explicitly configured
  `DATABASE_URL` environment variable; the `config` localhost fallback does not
  authorize a write. Checked before the connection is even opened.
- **Verified READ COMMITTED.** The connection is pinned to READ COMMITTED (a
  failure to pin is **not** swallowed) and the level is independently confirmed
  with `SHOW transaction_isolation`; REPEATABLE READ / SERIALIZABLE are rejected.
- **Catalog‑exact topology.** A bounded, closed **catalog manifest** — not just a
  name list — certifies the objects the bridge writes or depends on, resolved
  against `current_schema` (see *Connection namespace*):
  - **relations** — exact relation name **and relkind**, for the v47/v51→v61 main
    schema and the dedicated v59/v60 `research_evidence_automation_roi` schema;
  - **trigger functions** — frozen by **behaviour**, not only identity. Function
    identity alone is forgeable: `CREATE OR REPLACE FUNCTION
    slicea_reject_mutation() RETURNS trigger … BEGIN RETURN NEW; END` keeps the
    schema, name, identity arguments and result type intact while **neutralising
    the append‑only guard**. So each of the nine protected trigger functions is
    certified against a bounded semantic manifest: schema, name, identity
    arguments, result type **and `prorettype`**, `pronargs`, language, `prokind`,
    `proretset`, `pronargdefaults`, `provariadic`, `prosecdef`, `proconfig`
    (the fixed `search_path` where canonical), `provolatile`, `proisstrict`,
    `proparallel`, a body fingerprint **`md5(prosrc)`**, and an **exact overload
    count** (exactly one function may carry a protected name). These values are
    **not uniform** and are not assumed to be: the v47 `slicea_reject_mutation`
    is SECURITY **INVOKER** with **no** `proconfig`, while the v52–v61
    prepare/validate functions are SECURITY **DEFINER** with
    `search_path=pg_catalog`. The manifest was captured from a clean disposable
    full‑topology introspection and cross‑checked against the ratified migration
    definitions; a PG test re‑derives every value from a clean topology so the
    manifest cannot silently drift from the migrations. `proowner` is
    deliberately **not** frozen — under a clean apply the v47 function is owned by
    `workflow_migration_owner` and the v52–v61 functions by the bootstrapping
    superuser, so ownership reflects the migration *application path* rather than
    a ratified invariant (the **dedicated schema's** owner *is* checked, under
    *topology security*). This closure is bounded to the write‑boundary trigger
    functions — the bridge is **not** a general migration validator;
  - **write‑boundary triggers** — for every ledger the bridge writes
    (`candidate_fact_revision`, source/fact metadata, claim drafts/events,
    intake/items, review, freshness, claim support, project context, claim
    annotations, usage authorizations): the append‑only mutation guard
    (`*_no_mutation` → `slicea_reject_mutation`) plus each ledger’s
    preparatory/validation trigger. Each trigger must bind (`tgfoid`) to the
    **exact certified function OID** returned by the function manifest above — so
    a trigger pointing at a same‑named function whose body or properties drifted
    is rejected, and a function that fails certification fails its triggers closed
    (`func_not_certified`). The bound function is additionally checked for its
    **schema + identity arguments + result type** (so a same‑name
    function in another schema is rejected — `proname` equality is **not**
    sufficient, and the function must resolve to `current_schema`), plus `tgtype`,
    enabled state, not‑internal, and the frozen trigger semantics
    (`tgnargs=0`, empty `tgargs`, empty `tgattr`/no column list, `tgqual IS NULL`,
    not deferrable, not initially deferred, `tgconstraint=0`). Per ledger the
    **complete** set of non‑internal triggers is compared to the manifest —
    **extra** triggers are rejected as well as missing/drifted ones;
  - **load‑bearing request‑id uniqueness** — the UNIQUE constraints that make the
    documented idempotent retry actually hold. The repositories pre‑read the
    request before inserting, but at READ COMMITTED that pre‑read is **not** a
    guard: two concurrent callers can both observe “no such request”, and each
    ledger’s prepare trigger serialises only the **sequence allocator**
    (`SELECT … FOR UPDATE`), which hands out two *distinct* sequences rather than
    rejecting the second caller. The UNIQUE constraint is what turns the loser’s
    INSERT into the 23505 that the repository recovers the winner’s row from (e.g.
    `review_repository.insert_decision` keys recovery on the constraint **name**
    `uq_reird_item_request`). Without it, two rows commit for one `request_id` —
    silently, with no error anywhere. The manifest therefore freezes six
    constraints, one per request‑id‑bearing write path:

    | constraint | relation | ordered columns |
    | --- | --- | --- |
    | `uq_reird_item_request` | `research_evidence_intake_item_review_decision` | `project_id, research_evidence_intake_item_id, request_id` |
    | `uq_reifa_item_request` | `research_evidence_intake_item_freshness_assessment` | `project_id, research_evidence_intake_item_id, request_id` |
    | `uq_recsa_pair_request` | `research_evidence_claim_support_assessment` | `project_id, claim_intake_item_id, evidence_intake_item_id, request_id` |
    | `uq_repcr_project_request` | `research_evidence_project_context_revision` | `project_id, request_id` |
    | `uq_recar_claim_request` | `research_evidence_claim_annotation_revision` | `project_id, claim_draft_id, request_id` |
    | `uq_reuad_scope_request` | `research_evidence_usage_authorization_decision` | `project_id, claim_intake_item_id, evidence_intake_item_id, usage_scope, request_id` |

    Names and ordered columns were derived from the ratified v54/v55/v56/v61
    migrations, and a static test re‑parses those migrations so the manifest
    cannot drift from them. Each is verified for: exact `current_schema`, exact
    relation, exact constraint name, `contype='u'`, the **exact ordered** `conkey`
    columns, `convalidated`, **not** deferrable, **not** initially deferred — a
    DEFERRABLE constraint reports its violation at COMMIT, past the repository’s
    per‑statement recovery — plus the **backing index** that actually enforces it:
    same relation, unique, valid, ready, live, immediate, and neither an
    expression nor a partial index. This is deliberately **not** every CHECK/FK/
    index in v47–v61; it is exactly the idempotency contract of the bridge’s own
    write surface;
  - **roles** — exact relevant attributes (not names);
  - **v59/v60 topology security** — dedicated‑schema owner; the canonical
    owner→migration‑owner membership validated by its **exact PG16 options**
    (admin=false, inherit=false, set=true), not just the role names; **no
    transitive runtime escalation** — a recursive `pg_auth_members` traversal (not
    a fixed‑depth join) rejects any direct or indirect membership path from
    `workflow_automation_roi_runtime` to the research‑evidence owner or migration
    owner; and the runtime‑role schema ACL (USAGE, not CREATE).
- **Connection namespace.** `current_schema` is verified and reported, and is
  folded into the runtime fingerprint; the canonical ledgers must resolve into
  `current_schema`, so an unqualified **decoy schema** on `search_path` cannot
  satisfy the manifest.
- **Parent + source.** The parent project (and, where relevant, the source
  snapshot) must exist.
- **Pinned runtime identity.** The operator must pass `--expect-runtime-fingerprint`
  (obtained from `preflight`); the bridge derives the live fingerprint from
  `current_database` / `inet_server_addr` / `inet_server_port` / `configured_port`
  / `system_identifier` / `current_user` / `current_schema` and refuses to write
  on any mismatch. The DSN is never printed. Because this project runs
  PostgreSQL over a **Unix‑domain socket** — where `inet_server_addr()` and
  `inet_server_port()` are both `NULL` — `database`/`user`/`schema` alone cannot
  tell two local clusters apart. The identity therefore folds in a stable,
  non‑secret **cluster discriminator**: `pg_control_system().system_identifier`
  (the control‑file identity fixed at `initdb`) and the configured `port` GUC
  (`current_setting('port')`), so two socket‑backed clusters sharing
  database/user/schema still fingerprint apart. The identity **fails closed** if
  the live role cannot supply `system_identifier` (e.g. it cannot execute
  `pg_control_system()`): it raises `BridgePreflightError` rather than silently
  degrading to the collision‑prone address/port‑only fingerprint. No DSN,
  credential, connection option, or data directory ever enters the emitted
  identity. A **two‑cluster socket adversarial probe** starts two disposable
  socket clusters with deliberately identical database/user/schema, shows the
  pre‑fix dimensions collide byte‑for‑byte, then proves `system_identifier` and
  the corrected fingerprint differ — and that a real bridge write pinned to
  cluster A's fingerprint is refused against cluster B before any service write.

These are proven at the PG level with **catalog‑drift probes** that keep every
table name but drift one catalog fact — each blocks the **actual write command**
before its service runs and leaves the target ledger unchanged: drop / disable an
append‑only trigger; attach a trigger to the wrong function; a **same‑name
function in a decoy schema** while the canonical current‑schema function remains;
a mutation guard recreated with `WHEN (false)`, with `UPDATE OF` a column, or with
trigger arguments; an **extra** non‑internal trigger on a ledger; a wrong
schema‑local function signature; **transitive** runtime‑role escalation
(runtime → intermediate → owner, and → migration owner); a canonical
membership‑option drift; a dedicated‑schema owner or ACL drift; and a decoy
`search_path`.

**Function‑semantics probes** close the identity‑is‑not‑behaviour gap. Each keeps
the schema, name and signature canonical and drifts exactly one semantic fact:
the append‑only guard **recreated with a `RETURN OLD/NEW` no‑op body** (the
mandatory body‑drift probe — a companion test proves that body genuinely makes
the ledger mutable, so blocking it is load‑bearing); a **prepare function with a
changed body** but unchanged signature, result, security posture and
`search_path`; `SECURITY DEFINER → INVOKER` on a canonically‑definer function and
`INVOKER → DEFINER` on the canonically‑invoker guard; a repointed fixed
`search_path`; an added `proconfig` on the canonically‑unconfigured guard;
`VOLATILE → IMMUTABLE`; added `STRICT`; `PARALLEL SAFE`; and an **extra overload**
of a protected name. Each asserts `functions_ready=false` with the exact reason,
that dependent triggers fail closed as `func_not_certified`, that the real write
returns non‑zero with `error_type=BridgePreflightError`, that the target ledger
row count is unchanged, and that the bridge **never repairs** the drift. A
further probe rebinds a trigger to a same‑named function so `tgfoid` no longer
matches the certified OID while `functions_ready` stays true, proving the OID
binding is checked independently.

**Request‑id uniqueness probes** close the idempotency contract. Each drifts one
load‑bearing constraint and proves the **corresponding real write command** is
blocked (`review-record`, `freshness-record`, `claim-support-record`,
`context-record`, `annotation-record`, `authorize-internal-analysis`), that
`constraints_ready=false` with the exact `relation.constraint:reason` while every
other readiness category stays true, that the target ledger is unchanged, and that
the bridge **never repairs** the constraint: the constraint dropped; replaced by a
**same‑named non‑unique index** over the same columns; recreated with the **wrong
ordered columns**; recreated with a **widened key** (which would admit two rows per
`request_id`); recreated `DEFERRABLE` and `DEFERRABLE INITIALLY DEFERRED`; a
same‑named UNIQUE on a **different relation**; and each of the other five
constraints dropped in turn.

A **concurrency proof** shows the constraint is genuinely load‑bearing rather than
decorative. Two real READ COMMITTED callers use the canonical review
service/repository on one `request_id`: caller A inserts and holds the allocator
lock uncommitted; caller B’s pre‑read observes no request and its INSERT blocks in
the prepare trigger until A commits. With `uq_reird_item_request` **absent** both
callers commit **two distinct decisions under one `request_id`** — the documented
retry contract silently broken; the same test then shows the production bridge
refuses to write at all in that state. On **clean** topology the identical
interleaving yields exactly **one** row: the loser recovers the winner’s record
from the named 23505, and a repeated bridge `review-record` with the same
`--request-id` returns the same decision id without appending. The drift exists
only in the test’s disposable schema — no production bypass is introduced.

A wrong fingerprint, a non‑READ‑COMMITTED level, and a failed
isolation configuration likewise block; the correct fingerprint against the full
topology permits both dry‑run and commit. This is the bounded write‑boundary
contract only — it is **not** a general migration validator.

## Authorization / revocation safety

`usage_scope` is mechanically fixed to `internal_analysis`
(`FIXED_USAGE_SCOPE_VALUE`); there is no operator‑selectable scope option
anywhere in the tool. Before any commit the bridge displays a bounded,
non‑secret authorization preview (project, claim/evidence identity, current
annotation/support/claim‑review/evidence‑review identities, epistemic status,
confidence label, limitations, does_not_prove, decision scope `internal_analysis`
only, and the explicit list of scopes authorization does **not** extend to:
operator_dossier, client_report, exports, publication, any other scope). Because
the authorization is about the **evidence** item, the preview exposes
`evidence_source_citation_label` read through the **evidence** endpoint’s source
metadata revision (`evidence_ctx.source_metadata_revision_id`), and exposes the
claim’s own `claim_source_citation_label` separately — the two labels are never
collapsed into one ambiguous field. A commit additionally requires a typed
`--confirm` value that
exactly echoes `<project_id> <claim_intake_item_id> <evidence_intake_item_id>`;
a mismatch never emits a COMMIT. Eligibility remains owned by A‑2.

## Read‑only previews & byte budget

`pack-preview`, `projection-preview`, `authorization-list`, `project-show`,
`source-list`, and `trace-inspect` open a read‑only, no‑commit connection.
`projection-preview` computes the complete rendered UTF‑8 byte size with the
**same A‑4A renderer** and reports exactly one of `EMPTY`, `WITHIN_LIMIT`,
`WOULD_BLOCK_PROMPT_OVERFLOW`, or `WOULD_BLOCK_CAPACITY_OVERFLOW`. It never
truncates. The `rendered_utf8_bytes` contract reports only what was actually
rendered:

- `EMPTY` → `rendered_utf8_bytes = 0`;
- `WITHIN_LIMIT` → the actual complete UTF‑8 byte size;
- `WOULD_BLOCK_PROMPT_OVERFLOW` → `rendered_utf8_bytes = null` (an over‑budget
  block was measured but not admitted; no partial block is emitted);
- `WOULD_BLOCK_CAPACITY_OVERFLOW` → the field is **omitted** — no projection was
  assembled, so no byte size exists (it is not fabricated as `0`).

Boundary behavior at 65,535 / 65,536 / 65,537 bytes is proven against the real
budget.

## `trace-inspect` reads the persisted attestation

`trace-inspect` reports the Research Evidence consumption A‑4A **actually
persisted**, never a simulation. It reads the persisted `ProjectState` from
`state_snapshots` on the read‑only bridge connection (it does **not** call the
async project‑store loader, so it never creates tables or opens a write‑capable
pool), validates it through `ProjectState`, and reports the stored attestation
per phase via the canonical `build_phase_research_evidence_impact`. A phase with
no persisted consumption event is `not_recorded` / `consumed=false`; an existing
event returns its exact stored status, fingerprint, policy identity, counts, and
sources; the `report` phase is always `not_applicable`. It never infers
historical consumption from the current A‑3 projection, and it creates nothing.

**Malformed persisted state** has two forms, and both are reported identically —
`state_present=true`, `state_valid=false`, each consumer phase `invalid_state` /
`consumed=false`, a bounded non‑secret warning naming only the failure condition,
`report` `not_applicable`, exit 0 — never `not_recorded`, never a generic command
error, and never a fall‑back to the current projection:

1. **`state_json` that fails `ProjectState` validation.**
2. **ProjectState‑valid JSON whose nested persisted Research Evidence attestation
   cannot be reconstructed by the canonical `build_phase_research_evidence_impact`.**
   `ProjectState` does not type its policy events (`policy_audit_log: list[dict]`),
   so a model‑valid state can still carry a malformed
   `research_evidence_consumption` attestation — e.g. a non‑numeric count, or a
   `counts` value that is not a mapping. Decoding the persisted attestation is
   therefore a **second validation boundary**: both consumer‑phase impacts are
   built up‑front inside it, so one malformed attestation invalidates the whole
   history consistently rather than yielding a partially trusted trace. The
   boundary wraps **only** the pure‑Python impact projection over the
   already‑read state — never the database read — so a database error can never
   be reinterpreted as malformed state, and an absent/unavailable database is
   never hidden as invalid state.

Because the project‑store loader is deliberately avoided, `state_snapshots` may
not exist at all — state persistence may never have initialized. That is a
legitimate "nothing was ever persisted", not an error: the command reports
`state_present=false`, `state_valid=null`, both consumer phases `not_recorded` /
`consumed=false`, `report` `not_applicable`, and a bounded non‑secret warning
naming the uninitialized persistence. Absence is established by a **read‑only
`to_regclass` existence probe run before the `SELECT`**, never by catching a
database error: the probe keeps the read‑only transaction valid, needs no
exception recovery, and makes it impossible for an arbitrary database failure to
be reinterpreted as absence. The relation is never created. PostgreSQL coverage
proves the absent‑table report, that no table is created, that the connection
stays read‑only with zero writes/DDL and zero commits, and that the
table‑present cases (no project row, valid state, malformed state) are
unchanged.

The canonical `ResearchEvidenceImpactSummary` does not expose the rendered block
byte size, so trace‑inspect **omits** a per‑phase `rendered_utf8_bytes` rather
than fabricating a `0`/`null`; the current rendered byte size remains available
from `projection-preview`.

## Preflight

`preflight` is a **diagnostic only** (writes enforce their own copy of these
checks — see *Fail‑closed write preflight*). It reports, without mutation, both
feature gates, whether `DATABASE_URL` is explicitly configured (never printing
it), connection availability, the active runtime database, a bounded non‑secret
**runtime fingerprint** and its identity components (`current_database`,
`inet_server_addr`, `inet_server_port`, `configured_port`, `system_identifier`,
`current_user`, `current_schema`), and
the seven **catalog readiness categories** — `relations_ready`,
`functions_ready`, `triggers_ready`, `constraints_ready`, `roles_ready`,
`topology_security_ready`, `namespace_ready` — each with its own bounded
diagnostics list (`bad_constraints` reports `relation.constraint:reason`).

Readiness fidelity: a single `writes_allowed` boolean never stays true when a
supplied target check fails. Preflight distinguishes `research_writes_allowed`
(whole‑topology eligibility), `fact_writes_allowed` (additionally requires the
snapshot capture flag), `requested_target_ready` (flips false on a missing
project, missing snapshot, or `--expect-database` mismatch), and `writes_allowed`
as the conjunction relevant to the supplied arguments.

## Privacy / redaction

Default output is metadata‑safe. The tool never prints DSNs, secrets, storage
paths (`storage_ref`/raw `source_locator`), private content, or raw payloads.
Unexpected errors report only the exception class, never a traceback or message
that could carry a DSN. No raw‑excerpt operator option is added in this wave.
